# 万字干货！Harness Engineering 如何工程化落地？

> 来源：[万字干货！Harness Engineering如何工程化落地？](https://mp.weixin.qq.com/s/77dyufF3MP8stHPS0BApNw) | 作者：白家杰 | 来源：腾讯云开发者

Harness Engineering 的概念已经火了有一阵了，全网很多文章基本都是在讲理念，讲为什么今天做 AI 开发，不能只靠一段提示词，也不能把模型当一个"更聪明的代码补全"。但与此同时，一个问题也在持续地发酵：

> **理念我理解了，可是真正落到工程里，我第一步到底该做什么？**

这个问题特别重要。因为 Harness 这个词听上去很大，很像一个抽象的方法论，但它如果不能落到工程、目录、文档、脚本、工作流里，那它最后就只是一句漂亮的话。事实上，不同项目落地出来的 Harness，表面上可能完全不一样。有的项目是 CI 很强，有的项目是规范很强，有的项目是多 Agent 很强，有的项目甚至只是把几个脚本和模板整理得非常扎实。但如果你往下挖，会发现它们解决的其实都是同一个问题：

> **如何让 AI 在你的项目里，持续、稳定、规范、顺畅地做出你真正想要的结果。**

这一篇就拿 **JK Launcher** 这个真实工程做例子，把我们这一路是怎么一步一步把 Harness 搭出来的，原原本本讲清楚。哪些地方有效，哪些地方踩坑，哪些东西一开始以为够用，后来发现完全不够，都会写出来。

本篇文章字数非常多，一共分为12章，建议留足至少半小时的时间细读。

## 01 第一章：先把几个最容易混淆的概念讲清楚

> **很多人一上来就开始写 Rule、搞 Agent、接 MCP，最后越做越乱，根本原因不是执行力不够，而是概念没分清楚。**

先把这几个概念压成一张速览表：

| 概念 | 它主要回答什么问题 | 在我们工程里的角色 |
| --- | --- | --- |
| Rule | 什么事绝对不能乱来 | 基础规矩、红线、底线 |
| Skill | 这件事具体应该怎么做 | 固定动作的标准操作手册 |
| Sub Agent | 复杂任务由谁分工处理 | 不同阶段的专业角色 |
| Workflow | 这些角色按什么顺序接力 | 前进、暂停、打回、重跑规则 |
| Scripts | 最后谁来判断到底做没做好 | 统一门禁和事后验证 |
| MCP | AI 怎么安全接上外部工程系统 | 外接能力与工具链 |

### 1.1 Rule 是什么

Rule 可以理解成你给 AI 写的一套"工程规矩"。

它不是需求文档，也不是设计方案，更不是脚本。它更像是你在带一个新人开发时，先告诉他的那些基础原则：什么能做，什么不能做；什么做完必须验证；什么约定绝对不能绕过去。

所以 Rule 的核心作用，不是帮助 AI "变聪明"，而是帮助 AI **少犯一些本来不该反复犯的低级错误**。

但这里有个很重要的前提：**Rule 只是软约束，不是硬门禁。**

### 1.2 MCP 是什么

MCP（Model Context Protocol）本质上是一种标准方式：把「仓库之外的能力」接进 AI 的工作链路里——既能拉取信息，也能在明确边界内触发外部系统的动作。

所以在我们的整体拼图里，MCP 不是 Harness 的主体，而是 Harness 的外接能力接口——接什么、接到多细、何时允许接，本身也要被制度与门禁管住。

### 1.3 Skill 是什么

Skill 本质上是在告诉 AI：有些事情你不要临场发挥，不要每次重新理解，也不要自己"猜一个大概的流程"，而是严格按照这套固定步骤执行。

它很像给 AI 写的一份**标准操作手册**。Rule 告诉 AI "这件事必须做"，Skill 告诉 AI "这件事具体应该怎么做"。

### 1.4 Sub Agent 是什么

Sub Agent 就是多个"分工明确的 AI 角色"。

一个人既做产品、又做架构、又做开发、又做 QA，最后质量一定很难收口。所以我们后来引入了多个 Sub Agent，把不同阶段拆开。每个 Agent 只负责自己那一段，把产出写进文档，然后交给下一个 Agent。

### 1.5 Workflow 是什么

Workflow 最形象的理解方式，不是流程图，而是**接力赛规则**。

接力赛最重要的，不是有四个跑得快的人，而是下面这些事情必须先说清楚：第一棒是谁跑，第二棒什么时候能接棒，接棒的时候必须交什么，哪种情况算犯规，犯规以后是重跑、罚时，还是直接取消成绩。

如果没有 Workflow，工程现场通常会变成：需求不清楚，方案设计直接自己改需求；方案有问题，开发硬着头皮继续做；测试发现阻塞问题，PM 为了赶进度想办法往下推。

### 1.6 Scripts 是什么

Scripts 是整个 Harness 里最"硬"的东西。

如果说 Rule 只是告诉 AI 应该怎么做，Skill 只是给 AI 标准步骤，那 Scripts 就是在说：你说你做完了没用，得跑过我这关才算。

### 1.7 概念串起来

| **Rule**：告诉 AI 什么是规矩 | **Skill**：告诉 AI 规矩里的固定动作怎么做 | **Scripts**：不是告诉 AI，而是直接检查它做没做到 |
| --- | --- | --- |
| **MCP**：让 AI 接上外部知识和工具 | **Sub Agent**：把一个大任务拆成多个角色协作 | **Workflow**：规定这些角色在什么阶段、按照什么顺序协作 |

### 1.8 什么是 Harness Engineering

它不是某一个工具，也不是某一条提示词技巧，而是一整套让 AI 在工程里稳定产出正确结果的工程系统。三个关键词：**稳定**、**产出**、**正确结果**。

如果把我们当前工程里的 Harness 全貌摊开来看：

| 1 设计规格文档 | 2 Rule | 3 Skill |
| --- | --- | --- |
| 先把需求目标、边界、版本意图说透 | 把基础规矩和底线写死 | 把编译、测试、验证这类固定动作标准化 |
| **4 Sub Agent** | **5 Workflow** | **6 Scripts / 事后验证** |
| 把不同阶段拆成不同角色 | 把这些角色怎么接力说清楚 | 把很多约束真正落成可执行检查 |
| **7 开发导航地图（dev-map）** | **8 任务看板** | **9 MCP** |
| 让 AI 快速理解项目结构 | 让 PM 和需求分析知道项目进展 | 外部工程系统的连接能力 |

## 02 第二章：真正开始搭 Harness 之前，我先做了什么

### 2.1 工程画像：JK Launcher 在做什么

JK Launcher 本质上是一个面向 Unity 项目研发流程的桌面启动器工具。它不是一个单一功能的小工具，而是一整套围绕日常研发高频动作搭起来的工作台。它要处理的事情包括：

- 工程更新
- 打开和关闭 Unity
- SVN 环境检测与权限检查
- 冲突检测与冲突修复
- 定时更新和批量更新
- 更新失败后的诊断与恢复
- 多语言界面
- 日志、遥测、状态反馈

技术上，它的主体是一套典型的 Windows 桌面应用技术栈：以 WPF 为界面基础，以 .NET Framework 为主要运行时。

### 2.2 人搭 Harness，AI 写代码

这个工具在持续演进的过程中，真正的代码实现工作是完全由 AI 去完成的，人没有亲手写过一行代码。

人做的事情是一步一步把 Harness Engineering 搭起来：先把需求和设计说透，再补上规则，再把固定流程做成 Skill，再拆出多 Agent，再补上脚本门禁和事后验证，再补项目地图、任务看板和流程定义文件。

### 2.3 从设计规格文档（SPEC）开始

我们真正的第一步，不是写 Rule，而是先把一个比较完整的设计规格文档和 AI 反复磨透。

这类文档的意义，不是为了"文档看起来专业"，而是为了在项目一开始就把下面这些问题谈清楚：

- 这个版本到底要解决什么问题
- 哪些问题是核心目标，哪些只是顺手优化
- 改动会影响哪些模块
- 哪些行为必须保持兼容
- 最终什么样才算做完

最终的 SPEC 长什么样？它必须清晰的写明你的所有需求，指明必要的边界条件，必须没有任何不确定的词语，例如：建议，可以，推荐，可选等字样。

但很快我就发现，只靠这份文档，AI 还是会出问题。它不会百分之百按文档执行，做完以后很难知道到底做到哪了，很多错误会反复犯。

于是我们才进入下一步：给 AI 上 Rule。

## 03 第三章：Rule 很重要，但不要迷信 Rule

当时我的直觉很简单：既然 AI 经常忘事，那我就把容易忘、容易错的事情写成 Rule。

Rule 一上去，最粗糙的问题会立刻少很多。但如果你真的在复杂项目里跑过一段时间，你会很快发现 Rule 的天花板。

### 3.1 AI 会忽略 Rule

不是完全不看，而是会在复杂任务下"局部遗忘"。尤其当你的需求很长、上下文很重、同时加载了很多别的内容以后，一些 Rule 在实际执行时会被稀释掉。

### 3.2 AI 会绕过 Rule

这个比忽略更麻烦。因为它不是不知道规则，而是会开始给你找理由。比如：

- 这次不通过不是我引入的，是之前遗留的
- 这个 Rule 说的是常规需求，这次是特殊情况
- 我已经做了等价验证，不需要完全照规则来

Rule 不是没用，而是 Rule 只能做"原则约束"，不能做"流程执行"。

## 04 第四章：为什么要把编译、测试、验证做成 Skill

工程里有一类事情非常适合做成 Skill：执行步骤固定、每次都要做、做错一次就很恶心、不值得让 AI 每次重新思考。

编译、单元测试、事后验证，就是这一类事情。

这样做的好处特别直接：

1. **Rule 变轻了** — Rule 可以只保留真正的红线，复杂的执行步骤都交给 Skill
2. **AI 的执行稳定性变高了** — 它不是理解，而是调用一套现成的方法
3. **维护成本更低了** — 比如你后来修改编译流程，只需要改编译 Skill 本身

这一步做完以后，我们整套系统的健壮性明显提升了一截。但新的问题很快又出现了：单个 Agent 在复杂需求下，还是不够稳定。

## 05 第五章：为什么我最后一定会走到结构化的多 Agent

前面在 SPEC、Rule、Skill 这几层补齐以后，我们已经明显感觉到系统比最早稳了很多。但当需求继续变复杂以后，一个新的问题开始越来越明显：

单个 Agent 很难在长时间、复杂链路的开发里，同时把需求理解、方案设计、风险判断、编码实现、代码自审、测试验证都做好。

### 5.1 第一种做法：继续强化单 Agent

这条路我们其实已经走过一段。但问题在于，越往后走，越像是在把越来越多的责任塞进一个"大而全"的角色里。需求分析和代码审查，本来就不是同一种工作；方案设计和测试验证，本来就不是同一种思考方式。

### 5.2 第二种做法：去中心化协作

让多个 Agent 平起平坐，通过对话和协商动态达成共识。优点是足够灵活，缺点是行为路径不稳定、责任边界不够明确、后续换模型换维护人时很难保持一致。

### 5.3 第三种做法：结构化调度

把多 Agent 做成一条有明确角色分工、有明确流转规则的结构化流程。我们最后坚定地选了它，因为到了真实工程阶段，你会越来越清楚一件事：**真正贵的不是 token，真正贵的是失控。**

| 路线 | 看起来最吸引人的地方 | 真正的问题 | 最后的结果 |
| --- | --- | --- | --- |
| 继续强化单 Agent | 成本最低、改造最少 | 角色冲突越来越严重 | 早期有效，不能成为最终形态 |
| 去中心化协作 | 灵活、像 AI 团队讨论 | 路径不稳定、责任不清 | 被明确放弃 |
| 结构化调度 | 流程清晰、可审计 | 前期设计成本更高 | 最终选择的主路线 |

## 06 第六章：七个 Agent 不是拍脑袋拆出来的

### 6.1 第一步，先拆需求分析、方案设计、开发实现

最早我们碰到的核心问题，是"模糊需求直接流进代码"。所以最先拆出来的，是三层最基础的角色：

1. **需求分析** — 负责把模糊想法变成结构化需求
2. **方案设计** — 负责把需求翻译成真正能落地的技术方案
3. **开发实现** — 负责按照前面的约束去写代码

### 6.2 第二步，再补上闸门总控

需求写出来了，方案也写出来了，并不代表它真的已经具备进入开发的条件。于是我们补出了第四个关键角色：**闸门总控（可行性分析）**，专门判断需求够不够清楚、方案有没有明显漏项、这件事能不能安全落地。

### 6.3 第三步，再把代码审查和测试独立成最后收口

开发说自己做完了，不等于真的做对了。于是我们又把下游收口拆成了两层：

1. **代码审查** — 从实现层回头看有没有偏离需求、偏离方案、代码结构是否合理
2. **测试验证** — 从行为层看功能跑起来是不是对的、用户路径能不能走通

### 6.4 第四步，再补一个只做路由的 PM

我们需要的不是一个"最懂研发的 PM"，而是一个"最守流程边界的 PM"。它只负责流程流转、阶段判断、交接记录和任务推进，不负责专业判断。

### 6.5 为什么最后会稳定成这七个 Agent

| 1 项目经理（PM） | 2 需求分析 | 3 方案设计 |
| --- | --- | --- |
| 负责路由、交接、回退和进度管理 | 负责把模糊诉求变成清晰需求 | 负责把需求变成技术方案 |
| **4 闸门总控** | **5 开发实现** | **6 代码审查** |
| 负责开发前的可行性和风险把关 | 负责真正落地代码和实现细节 | 负责技术收口 |
| **7 测试验证** | | |
| 负责功能正确性、稳定性收口 | | |

| 需求分析解决"想做什么" | 方案设计解决"打算怎么做" | 闸门总控解决"现在能不能做" |
| --- | --- | --- |
| 开发实现解决"真正把它做出来" | 代码审查解决"是不是按要求做出来" | 测试验证解决"做出来的东西到底能不能用" |
| PM 解决"整条链怎么有序地串起来" | | |

### 6.6 给不同 Agent 配不同档位的模型

不同 Agent 的工作性质，决定了它们对模型能力的要求并不一样。PM 只负责流程流转，用性价比高的模型就够了；而需求分析、方案设计、代码审查这类角色，承担的专业判断更重，更适合配更强一点的模型。

## 07 第七章：真正落地以后，这套多 Agent 又是怎么一轮一轮补稳的

### 7.1 第一轮问题：下游开始自己修改上游文档

我们后来明确加了一条非常重的规则：**下游不能直接改上游文档。当下游认为上游产出不合格时，只能提出阻塞项，由 PM 把流程正式打回给上游。**

### 7.2 第二轮问题：PM 太容易越界

PM 很容易从流程管理者，滑成一个到处给意见的人。我们后来对 PM 的职责做了严格收缩：PM 只负责流程管理，不负责专业判断。**它不是流程中央的"总专家"，而是流程中央的"总路由器"。**

### 7.3 第三轮问题：各个 Agent 的专业性都还不够

以代码审查和测试这两个 Agent 举例，它们在整条链里处在非常典型的收口位置。代码审查不再只是给代码意见，而是必须对照需求和方案；测试也不再只是走一遍流程，而是要站在真正收口的位置去看功能、边界、回归、稳定性。

### 7.4 第四轮问题：Rule 约束开始不够用了

很多已经写进 Rule 的基础约束，Agent 还是会时不时不遵守。Rule 再多，本质上还是自然语言约束。所以我们后来又往前走了一步：把很多能判定的约束，尽量落地成脚本。

### 7.5 第五轮问题：Agent 会偷懒，于是又补了基线对比

它会告诉你"这次不通过不是我造成的"。于是我们又补了一层：开发前先跑一次，开发后再跑一次，做基线对比。如果开发后新增了错误、失败、Warning 增量，就必须修。

### 7.6 第六轮问题：流程本身也开始难维护了

我们大概补了三层东西：

**第一层：把流程结构单独抽成流程定义文件** — 有哪些阶段、每个阶段默认由哪个 Agent 负责、正常应该怎么往前走、出问题时允许退回到哪。

**第二层：把每个 Agent 的输入输出抽成角色契约** — 这个角色必须读哪些上游产物、必须写出哪些文档结果、什么情况下有权提出阻塞。

**第三层：再补一个流程校验脚本** — 专门检查流程定义文件是不是存在、每个 Agent 对应的契约文件是不是齐全、流程里提到的角色能不能在契约里找到。

### 7.7 从 0 开始的最小搭建顺序

| 步骤 | 内容 |
| --- | --- |
| 1 | 先磨出一份能指导开发的设计规格文档 |
| 2 | 先补最关键的 Rule，不要贪多 |
| 3 | 把高频固定动作下沉成 Skill |
| 4 | 当单 Agent 开始失稳时，再拆多 Agent |
| 5 | 当多 Agent 开始变复杂时，再补流程定义文件和角色契约 |
| 6 | 当项目进入持续迭代时，再补 dev-map 和任务看板 |
| 7 | 当你想把闭环继续往外推时，再考虑 MCP |

## 08 第八章：为什么最后一定会走到 Scripts，尤其是总验证脚本

总验证脚本不是"建议你验证一下"，而是在客观上决定：这次开发到底算不算完成。

### 8.1 总验证脚本到底做了什么

它是一套"研发后验证总入口"：

**A 类：静态规范问题** — XAML 里是否出现中文、Emoji、是否使用了 C# 8.0+ 语法、是否有硬编码 UI 文本等

**B 类：基础交付门槛** — 编译必须成功、测试必须全部通过、测试数量不能异常减少

**C 类：工程一致性** — 规则文件是否完成多格式同步、.cs 文件是否都进了 .csproj

### 8.2 为什么这一步对 Harness 特别关键

从这一刻开始，AI 的完成定义不再是"我觉得我做完了"，而变成"脚本判定你通过了，你才算做完"。

### 8.3 为什么它最后会变成统一入口

以前这些动作可能分散在 Rule 里的一句话、Skill 里的某个步骤、Agent 自己的收尾说明、维护人脑子里的经验。但当它们被统一收进一份总验证脚本以后，开发完成的定义就第一次真正被收紧了。

## 09 第九章：如何让 AI 带上「整个项目的记性」

PM 和各个 Agent 缺乏整个项目的全局视野时，容易发生：新方案把旧方案冲掉，AI 重复造轮子。

### 9.1 dev-map：开发侧那本导航

规则写得很直白：改代码之前，先查 dev-map。它说的是：某个功能一般落在哪些文件、某类服务怎么接入、某类配置通常在哪定义、改一个模块可能会牵动哪些链路、项目里已有的标准写法长什么样。

这套东西由开发 Agent 在干活的过程中维护。谁改地貌，谁最有资格改地图。

### 9.2 任务看板：需求侧那张总览

由 PM 维护的项目级任务总览，一般会记：当前有哪些任务在做、每个任务进行到哪个阶段、对应的文档目录在哪、已完成任务的交付结论是什么。

dev-map 偏代码与模块结构从哪进门；任务看板偏需求和任务历史从哪进门。

## 10 第十章：团队级 Harness 里，Memory 为什么可以靠边站

> **事实像档案，例子像故事，规矩像手册——手册应进仓库，别只靠聊天记忆。**

| 类型 | 像什么 | 团队项目里更适合落在哪 |
| --- | --- | --- |
| 定了的结论、边界、任务与文档索引 | 档案 | SPEC、任务看板、设计说明 |
| "成功长什么样、失败长什么样" | 故事 | 测试用例、门禁脚本的输出约定 |
| 反复踩过的坑、绝不能碰的红线 | 手册 | 优先 Scripts，其次 Rule |

纯个人偏好用 Memory 无可厚非，但团队级 Harness 的目标，是**不依赖某个具体的人也能把事做对**。

## 11 第十一章：最后想聊聊人和 AI 的关系

### 11.1 在这个过程中，人到底在做什么

人从"执行者"逐步上移成了"系统设计者"和"最后责任人"：定义项目目标和边界、设计流程、制定规则、设计脚本门禁、审视流程漏洞、在流程卡住时做最终判断。

### 11.2 今后人和 AI 应该是什么关系

AI 不是助手，AI 更像是一支执行力极强但必须被制度化管理的团队。

- 人负责设计系统
- AI 负责在系统里高强度执行
- 人对最终结果负责

### 11.3 后续方向

**第一，更多规则继续脚本化** — 只要是能判定的，就尽量不要停留在 Rule 层

**第二，把流程进一步产品化** — 继续往更强的状态机、更强的自动校验上发展

**第三，做项目类型模板** — 沉淀出每类项目的"最小可用 Harness 模板"

**第四，把"知识"沉淀进项目** — 不应该越来越像"我和我的 AI 的默契"，而应该越来越像"任何一个人拿到这个工程，都能顺着这套系统做对事情"

## 12 第十二章：Harness 的全貌——四块拼图如何一起转

| 拼图 | 在 Harness 里管什么 |
| --- | --- |
| **约束与流程** | AI 该按什么顺序、什么边界做事；协作时谁接哪一棒 |
| **反馈** | 做完以后，系统能不能对结果有说法 |
| **知识库** | 项目级、写进仓库的「从哪进门」——索引优先 |
| **进化** | 规范与权威往哪沉淀；人退到哪一层；Harness 怎么继续变厚、变可交接 |

四块相辅相成，缺一块的典型症状：

- **只有流程没有反馈**：容易变成「看起来很忙、但不知道做对没有」的完成幻觉
- **只有反馈没有流程**：闸机有了，但上游仍是一团即兴
- **没有知识库**：同一类功能反复被重写、同一类坑反复踩
- **没有进化**：前三块容易冻在某一版

## 结语

Harness Engineering 不是为了让 AI 看起来更聪明，而是为了让 AI 在复杂工程里更可控、更可靠、更可维护。

这件事不会一次搭齐。你愿意从最痛、最反复的那一个问题开始，把规矩、技能、脚本和流程一点点沉进仓库，四块拼图就会自己长全。

**不要贪大，不要一步到位，先从你最反复、最痛的那个问题开始。**

| 模块 | 在 Harness 中的作用 |
| --- | --- |
| 约束与流程 | Rule / Skill / 多 Agent / Workflow 等，规定怎么接力、边界在哪 |
| 反馈 | 总验证脚本等，对结果是否过关给出可执行判定 |
| 知识库 / 索引 | dev-map、任务看板等写进仓库的项目级进门索引 |
| 进化 | 规范沉淀、人与 AI 分工，Harness 随项目持续改版 |
| 设计规格文档 | 统一版本目标、边界和实现方向 |
| Rule | 写死基础规范与底线 |
| Skill | 把固定动作标准化 |
| 总验证脚本 | 建立事后验证和反馈闭环 |
| 多 Agent 定义 | 固定角色分工 |
| 流程定义文件 | 固定阶段与迁移关系 |
| 角色契约 | 固定每个角色的输入输出边界 |
| 开发导航地图 | 帮助 AI 快速理解项目结构和已有模式 |
| 任务看板 | 给 PM 和需求分析提供全局视角 |
